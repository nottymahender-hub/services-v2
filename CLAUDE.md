# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`grc-orl-services-v2` — a Spring Boot 3.4 / Java 21 REST service (`com.dbs.mot.grc`) for GRC "Operational Risk Landscape" (ORL). It manages CSV-based maintenance of static/reference tables and serves landscape **assessments** (monthly snapshots of risk ratings by dimension), their drill-down details, and per-assessment **callouts**.

## Commands

The Maven wrapper (`./mvnw`, `mvnw.cmd` on Windows) is committed — use it.

```bash
./mvnw clean verify          # compile, run all tests, JaCoCo report + coverage gate
./mvnw test                  # run all tests (also produces JaCoCo report)
./mvnw spring-boot:run       # run the app (needs a MariaDB per application.properties)
./mvnw test -Dtest=BizUnitCsvHandlerTest              # single test class
./mvnw test -Dtest=BizUnitCsvHandlerTest#methodName   # single test method
```

- **Coverage gate:** JaCoCo enforces **≥90% line coverage** on the whole bundle during the `verify` phase (`jacoco:check`). A build can pass `test` but fail `verify` on coverage — keep new code covered. Report: `target/site/jacoco/index.html`.
- **Tests run against in-memory H2** (`src/test/resources/application-test.properties`), MySQL-compatibility mode, schema from `src/test/resources/schema-test.sql` (Flyway is disabled for tests). The production schema is Flyway migration `V1__create_all_tables.sql`. **These two schema files are maintained separately — when you change one, update the other**. H2 (MySQL mode) supports `DEFAULT CURRENT_TIMESTAMP` and `ON UPDATE CURRENT_TIMESTAMP` (used for the DB-managed audit timestamps), but not every MariaDB feature — notably not `ON DUPLICATE KEY UPDATE`, which is why the config upserts split insert/update in Java instead.
- Running the app locally requires MariaDB at `jdbc:mariadb://localhost:3306/grc_orl2_db` (root/root by default). Swagger UI is available at `/swagger-ui.html` when running.

## Architecture

### Package layout

There is **no `common` package** — all shared packages sit directly under `com.dbs.mot.grc`: `controller`, `service`, `repository`, `entity`, `dto`, `csv`, `exception`, `config`, `enums`, `validation`, `util`, `logging`.

### Two feature areas

1. **ORL configuration import/export** (`controller/OrlConfigurationController`, the `*ConfigImportService` beans in `service`, the shared engine in `csv`, plus `csv/mapper`, `csv/validator`) for the static/reference tables.
2. **Landscape assessment domain** (`controller/LandscapeAssmtController`, `service`, `entity`, `repository`, `dto`) — assessment generation, read/drill-down, overlay + commentary save, and callouts.

### ORL configuration pipeline

`OrlConfigurationController` (`/api/orl-configurations`) exposes an **explicit upload endpoint per table** (e.g. `POST /api/orl-configurations/biz-units/upload`) and a **single, shared download endpoint** `GET /api/orl-configurations/{configName}/download` (e.g. `.../biz-units/download`). Each table has its own `service/XxxConfigImportService implements OrlConfigImporter` (the payload is CSV, but each represents a *configuration*, so the classes are not named "Csv"). Uploads inject the importers directly and delegate the import+audit transaction to `OrlConfigurationService`. Downloads resolve the target importer by `configName` through `csv/OrlConfigImporterRegistry` (built from all `OrlConfigImporter` beans; unknown name → `NotFoundException`/404) — the only place with `{configName}` dispatch; uploads still have **no generic dispatch**.

`OrlConfigImporter` is split into two narrower interfaces it composes — `csv/ConfigUploader` (`configName`, `processAndImport`) and `csv/ConfigExporter` (`configName`, `getDownloadFilename`, `getDownloadHeaders`, `writeDataRows`) — since no caller ever uses both halves: `OrlConfigurationService.importConfig` and the controller's `upload(...)` helper depend only on `ConfigUploader`; `OrlConfigImporterRegistry` and the controller's `download(...)` helper depend only on `ConfigExporter`. Each `*ConfigImportService` still just `implements OrlConfigImporter` — the split needed no changes to any of the 8 importer classes.

**To support a new table:**
- `service/XxxConfigImportService implements OrlConfigImporter` — config name, headers, persistence.
- `csv/mapper/XxxCsvRowMapper implements CsvRowMapper<T>` — one CSV row → DTO, collecting per-cell/type errors.
- `csv/validator/XxxCsvRowValidator implements CsvRowValidator<T>` — cross-row/dataset checks.
- add an explicit **upload** endpoint to `OrlConfigurationController`. **Download needs no controller change** — the new importer auto-registers in `OrlConfigImporterRegistry` and is served by the shared `{configName}/download` endpoint under its `configName()`.

All importers delegate parsing to the shared `CsvImportProcessor.process(...)`: file validation → header validation (exact set, no duplicates, BOM-stripped) → per-row mapping → per-row Hibernate Bean Validation → dataset-level validation. Both mapping and cross-row phases collect **all** errors and throw `CsvValidationException` (→ HTTP 400 with per-row detail). `OrlConfigurationService.importConfig` is `@Transactional`, so the row import and the audit insert commit as one unit.

**Persistence is 100% Spring Data JDBC repositories — no `JdbcTemplate`/`NamedParameterJdbcTemplate`.** Append-only tables use `repository.saveAll`. The three **upsert** tables (`orl_biz_unit`, `orl_entity_mstr`, `orl_bu_loctn_headcount`) upsert *without* `ON DUPLICATE KEY UPDATE`: the service reads existing rows, splits incoming into inserts/updates, and calls `saveAll` on each (within-file duplicates keep the last occurrence). The two client-`@Id` entities (`OrlBizUnit`, `OrlEntityMstr`) implement `Persistable` with a transient `newRecord` flag so `saveAll` inserts new rows and updates existing ones; `OrlBuLctnHeadcount` matches on its composite unique key and reuses the surrogate id.

The three **scoring tables** (`feature_score_band`, `train_stats`, `net_risk_band`) compute `config_version` server-side via `ConfigVersionResolver` as `MAX(existing version for the natural-key group) + 1`. The current per-group maxima are read through a grouped `@Query` projection on each scoring repository (returning a `*VersionGroup` record); `ConfigVersionResolver` is pure in-memory logic. Open-ended range bounds use the sentinels in `RangeSentinels`.

**Table-specific validation notes:**
- `risk-type-risk-area-maps` upload carries `IS_OR_FA` (mandatory, `Y`/`N` only) and `RISK_CLUSTER` (optional). Its `CsvRowValidator` enforces two batch rules: `(RISK_AREA, RISK_TYPE_L4_NUM)` unique (mirrors the table key) and `RISK_CLUSTER` unique within each such pair (blank clusters ignored).
- `lndscp-dim` upload validates `BIZ_UNITS` against the distinct **`orl_biz_unit.ORL_BU_NM_L{level}`** matching the batch `BIZ_UNIT_LVL` (2→L2, 3→L3, 4→L4; other levels skip the ref-check) and `LOCATIONS` against the union of **`orl_entity_mstr.orl_location` and `orl_location_ic`**. Both sets are derived in `OrlLndscpDimCsvRowValidator` from `CrudRepository#findAll()` + in-memory distinct — Spring Data JDBC has no derived query for a single-/multi-column distinct scalar list, and both are small config tables.

The Flyway baseline `V1__create_all_tables.sql` is **fully idempotent** (`CREATE TABLE IF NOT EXISTS` on every table), so it can be re-applied safely after its history row is cleared (e.g. when a column is added to V1 rather than via a new versioned migration).

### Assessment domain model (Spring Data **JDBC**, not JPA)

This uses **Spring Data JDBC**. Key consequences that differ from JPA:
- FKs are modelled as `AggregateReference<T, Long>` — one-way, no cascade, no lazy navigation. Extract the id with `.getId()`.
- `OrlLndscpAssmt` owns its detail rows as a `@MappedCollection` (`orl_lndscp_assmt_details`). **Fetching the `OrlLndscpAssmt` entity eagerly loads all detail rows**, so use it only when you actually need them (the assessment listing). For existence use `existsById`; for header-only reads use the `findHeaderById` projection.
- **`save()` on an existing aggregate does a full delete+reinsert of its children.** So only call `save()` on the *collection-owning* `OrlLndscpAssmt` for a fresh insert, never to mutate an existing one. Child and childless rows, however, save cleanly: the overlay save loads the target `OrlLndscpAssmtDetails` by id (`findById`) and re-saves that single row via `detailsRepository.save(row.toBuilder()...)` — the detail is fetched and persisted as its own `CrudRepository` entity, not through the parent aggregate, so no delete+reinsert occurs. `OrlLndscpCallout` (no child collection) likewise updates/soft-deletes via `save()` on the loaded row (`toBuilder`). There is **no `@Modifying @Query`** and no `JdbcTemplate`/`NamedParameterJdbcTemplate` anywhere — all DB access is through repositories (`CrudRepository` methods + derived queries + a few read-only `@Query` projections).
- **Callouts:** field values are validated only by request-body Bean Validation (`@NotBlank`/`@NotEmpty`/`@Size(max=400)` on the comment) — there is no validation of values against the landscape dimensions, and the comment is rejected (400), not truncated, when too long. The active callouts are embedded in the assessment-details response as a plain `List<CalloutResponse>` (field `callouts`).
- **Timestamps are DB-managed.** `CREATE_DT_TM`/`CREATED_DT_TM`/`UPDATE_DT_TM`/`uploaded_dt_tm` columns are filled by the database (`DEFAULT current_timestamp()` on insert, `ON UPDATE current_timestamp()` on update) — never by the app. The entity fields carry `@ReadOnlyProperty` so Spring Data JDBC excludes them from INSERT/UPDATE; do not set them in builders. (H2 supports both `DEFAULT CURRENT_TIMESTAMP` and `ON UPDATE CURRENT_TIMESTAMP`, so the same behaviour holds in tests — keep the two schema files in step.)
- **Prefer single-table queries; join only to avoid a worse pattern.** Services mostly issue plain single-table queries (`findById`, derived queries) and merge in Java. Two deliberate joins exist, both to avoid a much worse access pattern: (1) the assessment **listing** projection (`findAllSummaries`) `LEFT JOIN`s `orl_lndscp_dim` to carry the landscape name in one query rather than loading every landscape config separately; (2) `FactOrlRepository.findMatchingByAssmtDetails` is a **semi-join** against `orl_lndscp_assmt_details` so the list drill-down (`fetchByAssmtId`) fetches only the `fact_orl` rows whose dimension key matches the assessment's own detail rows — not the whole business date's facts (which could be far larger than the assessment). It is run once for the current biz date and, only when `PREV_ASSMT_NUM` is set **and** at least one previous-month detail row has no overlay (`previousFinalRatings` checks this first), once for the previous biz date — when every previous-month row already carries an overlay, the fact fallback is never needed and the query is skipped entirely. The single-row drill-down uses the `findHeaderById` projection + targeted single-row detail reads (`findById` for the row — its id is the PK, so it is not scoped to the path assessment — and `findByAssmtAndDimension` for the previous month) so the assessment's detail `@MappedCollection` is never loaded for a single-row view; that collection is loaded only by `fetchByAssmtId`, which returns every detail row. The single `fact_orl`/module lookups are plain **derived queries** on the `CrudRepository`s (`findByBizDtAndRiskAreaAndOrlBuNmL2AndOrlBuNmL3AndOrlBuNmL4AndLocation(...)`), not `SELECT *` `@Query`s. The `@Query` methods on the fact/detail repos — `OrlLndscpAssmtDetailsRepository.findByAssmtAndDimension` and `FactOrlRepository.findMatchingByAssmtDetails` — filter on `lndscp_assmt_id`, the aggregate's `@MappedCollection` back-reference, which is intentionally unmapped on the child, so no derived-query property path can name it.

### The assessment/fact split (important)

Assessment detail rows (`orl_lndscp_assmt_details`) are **thin**: dimensions, category, status, overlay fields, the analyst-revised commentary (`REVISED_COMMENTARY` + its `COMMENTARY_REVISED_BY`/`COMMENTARY_REVISED_AT` audit — see the commentary note below), and audit columns. **There is no stored risk-rating-change column of any kind** (`RISK_RTNG_CHGE` and `MODULE_RISK_RTNG_CHGE` were removed) — every risk-rating change, overall and per-module, is derived fresh on every read; see the risk-rating-change note below. Row-level **computed** values (calculated NRR, control effectiveness, commentary, inherent risk) live in the separate `fact_orl` snapshot table (`CTRL_EFF_RTN` is a plain `VARCHAR` — surfaced as a raw string, not an enum), and the per-module **GRC metrics** live in the module snapshot tables (`rcsa_fact_orl`, `inc_fact_orl`, `ina_fact_orl`, `kri_fact_orl`, assembled by `GrcMetricsService` for the drill-down only). All are **matched at read time by dimension key** (`RISK_AREA`, `ORL_BU_NM_L2/L3/L4`, `LOCATION`) for a business date. The module tables are **standardized** on those same key column names plus `biz_dt` and `NET_RISK_RATING`, mapped in each entity (`ModuleFact`). `GrcMetricsService` **always names all four modules** in its `grcMetrics` map, in `RCSA → INC → INA → KRI` order, and **every block is always fully populated** (`GrcModuleBlock`): a module with no snapshot row is still present with `nrr = "N.A"` and lists **all** of its metrics with `value = null` and `riskRatingChge = "N.A"`, so the block's shape never varies. Each block is `{ nrr, riskRatingChge, metrics: [ { name, value, riskRatingChge } ... ] }` — `metrics` is an **ordered list** (canonical order from the entity's `metrics()`), not a map, and the metric names come from a per-module empty-instance template so the name set lives only in the entity. The business date used for each lookup is:
- current month → the assessment's own `biz_dt` (`orl_lndscp_assmt.biz_dt`)
- previous month → the previous assessment's `biz_dt` (followed via `PREV_ASSMT_NUM`)
- live → the latest business date across `fact_orl` (`findMaxBizDt()`), matched to the dimension via the same by-date lookup. That `MAX(biz_dt)` is read **once** and reused for both the live snapshot and the response's top-level `lastRefreshed` (so `live.lastRefreshed == lastRefreshed`, and there is no second `findMaxBizDt` call). If the dimension has no row on that global latest date, `liveNRRDetails` is `null`.

The displayed `nrr` is the analyst overlay (`OVRLY_NET_RISK_RTNG`) when present, otherwise it falls back to the calculated rating (`nrrCalculated`) — in both the list items and the current/previous drill-down blocks (`nrrOverlaid` records which applied).

**Net risk rating is returned as the stored DB value.** The per-module fact tables use `NET_RISK_RATING` (renamed from `NET_RISK_RTNG`); `fact_orl` keeps `CAL_NET_RISK_RTNG`. Every net-risk-rating field in every response — the list items (`nrrCalculated`/`nrr`/`prevAssmtFinalNRR`) and the drill-down blocks' `nrr` — is the **stored DB value** (`PersistableEnum.dbValue`, e.g. `"Med Low"`); there is no display label.

**Risk-rating change is always derived, never stored — same algorithm everywhere.** Neither the overall change nor the per-module/per-metric changes are persisted anywhere; they are computed on every read from whatever data is already there. Two rules, each isolated in one place, with **different labels at the module level vs. the metric level** — module-level change is severity-based (`Improved/Deteriorated/Stable/N.A`); metric-level change is a neutral numeric compare and uses `"No change"` instead of `"Stable"` for equality, to keep the two kinds of comparison visually distinct in the response:
- **Overall change** (the list items' `riskRatingChange`, and each drill-down block's `MonthNRRDetails.riskRatingChange`): `util/RiskRatingChanges.derive(previousFinal, currentEffective)`, where `currentEffective` is a dimension's effective rating (`LandscapeAssmtDetailsService.effectiveNrr` — the overlay when set, else the calculated rating) and `previousFinal` is that same dimension's effective rating **within a specific earlier assessment**. Two flavors of that lookup exist, used by different callers: `finalRatingFrom(detail, snapshot)` derives it from an **already-loaded** detail row + `Snapshot` with zero extra queries (used by the drill-down, which loads a `Snapshot` per period anyway for the GRC blocks); `finalRatingForDimension(assmtHeader, key)` fetches its own detail row (and, only if needed, its `fact_orl` row) — used by the overlay save, which has no other need for module facts and would waste a fetch pulling them just to reuse the snapshot-based variant. The overlay save derives the change the same way immediately after persisting, purely for the response — nothing is written back.
- **Module-level and per-metric change** (`GrcModuleBlock.riskRatingChge`, `GrcMetric.riskRatingChge`): `GrcMetricsService.buildBlocks(targetFacts, baselineFacts)` — the **single** method that builds every block (current, previous, and live all call it with different target/baseline pairs). Module change = `RiskRatingChanges.derive` of baseline vs. target NRR (`Stable` on equality); each metric's change is a neutral numeric compare (`Increased/Decreased/No change`, no severity judgement) between the target and baseline value, both `"N.A"` when either side is missing. Current block's baseline = previous assessment's module facts; previous block's baseline = the assessment before that; live block's baseline = the current assessment's own module facts.

**Severity rule** (`RiskRatingChanges.derive`, severity `LOW<MED_LOW<MED_HIGH<HIGH`): either side `null` → `N.A`; equal → `Stable`; less severe → `Improved`; more severe → `Deteriorated`.

**`fetchDetailById` reads as one linear algorithm, and fetches each business date's data exactly once.** The drill-down is structured as four sequential comparisons — current vs. previous (→ `currentMonthNRRDetails`), previous vs. previous-to-previous (→ `prevMonthNRRDetails`), and live vs. current (→ `liveNRRDetails`) — each built from a private `Snapshot` record (`bizDt` + `fact_orl` row + module facts) fetched once per period via `snapshotAt(bizDt, key)`. Each period's detail row (`detailRowFor(assmtHeader, key)`) is also fetched exactly once and reused everywhere it's needed within that request (e.g. the previous assessment's row and snapshot double as both the current block's comparison baseline and the previous block's own data) — no dimension/business-date pair is ever queried twice in one call. `previousAssmtHeader(assmtHeader)` walks one `PREV_ASSMT_NUM` hop and is composable (call it again on its own result to walk a second hop), replacing a separate null-safety helper.

**Response timestamps are UTC → SGT.** All `CREATE_DT_TM`/`UPDATE_DT_TM`-style audit columns are stored in UTC; every timestamp surfaced in a response (`AssmtDetailResponse.lastModifiedOn`, `LandscapeAssmtDetailSummary.lndscpLastModifiedOn`, `CalloutResponse.createdOn`/`updatedOn`, `LandscapeAssmtSummary.lastModifiedOn`) is converted to Singapore time via `util/SgtDateTimes.toSgt(...)` — the single place the +8h offset rule lives. The returned `LocalDateTime` carries no zone marker (the API keeps the plain date-time shape); the value is SGT wall-clock.

**Write endpoints echo what they persisted (plus derived fields).** There is a single write endpoint for a detail row: `POST .../assessmentDetail/{id}/overlay` persists `OVRLY_NET_RISK_RTNG`/`OVRLY_JSTFKN`/`REVISED_COMMENTARY` together in one save and returns `OverlayResponse` — the persisted fields plus `nrrOverlaid` (Y/N), `ctrlEffRtn` (read from `fact_orl` for the assessment's own business date — fetched unconditionally now, since it's needed regardless of whether an overlay is set), and `riskRatingChange` (derived fresh from the just-saved overlay, never written to the row). There is **no separate commentary endpoint** — `SaveAssmtDetailOverlayNRRRequest.revisedCommentary` covers it, and a request that omits/blanks it clears the stored commentary (mirroring how `overlaidNRR`/`overlayJstfkn` already behave), so a caller that wants to leave commentary untouched must resend its current value. Callout `POST`/`PUT` return the created/updated `CalloutResponse` (re-read so DB-managed timestamps are populated).

**Commentary-revision audit is change-detected, not unconditional.** `saveOverlay` stamps `COMMENTARY_REVISED_BY` (the `X-EGRC-UserId` header) and `COMMENTARY_REVISED_AT` (app-written in **UTC** — a normal column, not `@ReadOnlyProperty`) **only when** the incoming `revisedCommentary` actually differs from the row's current `REVISED_COMMENTARY` — an overlay-only save that resends the same commentary text leaves the existing reviser/timestamp untouched. Both are echoed in `OverlayResponse` and surfaced on the drill-down's per-month blocks (`MonthNRRDetails.commentaryRevisedBy`/`commentaryRevisedAt`, populated for **both** `currentMonthNRRDetails` and `prevMonthNRRDetails` from each block's own row) and at the top level (`AssmtDetailResponse.commentaryRevisedBy`/`commentaryRevisedAt`), with the timestamp converted UTC→SGT via `SgtDateTimes` like every other response timestamp.

**Proportions in the GRC metrics are percentages.** The KRI `KRI_RED_PROP`/`KRI_GREEN_PROP` (derived from the red/green counts over the active count) and the RCSA `rcsa_high_risk_proportion`/`rcsa_med_high_proportion`/`rcsa_med_low_proportion`/`rcsa_low_risk_proportion` (stored as 0..1 fractions) are all surfaced in the response as **percentages** — ×100, rounded to 2 dp, `HALF_UP` — via `util/Percentages` (e.g. `0.5433 → 54.33`, `2 of 4 → 50.00`). A `null` fraction or a zero KRI active-count stays `null` (distinct from `0.00`); the conversion happens in each module entity's `metrics()`.

Because MariaDB treats each NULL as distinct in a unique index, all dimension columns in `orl_lndscp_assmt_details` and `fact_orl` are `NOT NULL DEFAULT ''` — whatever populates these tables must write `''` (never null) for empty dimensions so the unique index actually enforces one row per dimension, and the read-time dimension-key match lines up between details and facts. Preserve this invariant.

### Assessment generation

`POST /landscape/assessments/generate` (`BulkAssmtGenerationService`) takes a **mandatory as-of date** query param `bizDt` (ISO `yyyy-MM-dd`) that **must not be in the future** — a missing param, a malformed date, or a future date each returns **400** (via `MissingServletRequestParameterException`, `MethodArgumentTypeMismatchException`, and a `BadRequestException` guard in the controller respectively). It generates the reported month's assessment for every landscape config that is `ACTIVE` and effective **on that as-of date** (`OrlLndscpDim.isActiveAndEffectiveOn(bizDt)`), grouped by landscape name. It is **intentionally not `@Transactional`**: each landscape is generated in its own transaction by `LandscapeAssmtGenerationService.generateForDim(dim, bizDt, userId)`, so one landscape's skip/failure never rolls back the others. Per-landscape outcome is reported as `GENERATED`, `SKIPPED_AMBIGUOUS_CONFIG` (more than one active config effective on the as-of date) or `SKIPPED_ALREADY_EXISTS` (this period already generated). The as-of date's month is **M**; the run reports the **previous** month **M-1**: `ASSEMT_PERIOD` = M-1, `biz_dt` = that month-end (else the latest `fact_orl.biz_dt` within M-1 via `findMaxBizDtBetween`), `PREV_ASSMT_NUM` links to the M-2 assessment. (E.g. `bizDt=2026-02-20` → January 2026, previous December 2025.) `generateForDim` expands `riskAreaNames × business units × locations` into `L{lvl}`/`grp_l{lvl}`/`loc` category rows, resolving BU names to their (L2,L3,L4) path from `orl_biz_unit`, and writes **only** dimensions, category, status and audit columns — it never touches `fact_orl` or the module tables, and computes no risk-rating change of any kind (that is entirely a read-time concern; see the risk-rating-change note above). The new aggregate is persisted with one `save()` (a fresh insert, so the delete+reinsert caveat does not apply).

### Cross-cutting conventions

- **Landscape endpoints** (all on the single `LandscapeAssmtController`): `GET /landscape/assessments` (list), `POST /landscape/assessments/generate` (bulk generation), `GET /landscape/assessments/{lndscpAssmtId}` (details **with embedded dimensions + callouts**), `GET /landscape/assessment/{lndscpAssmtId}/assessmentDetail/{assmtDetailId}` (drill-down), `POST .../assessmentDetail/{assmtDetailId}/overlay` (overlay **and** commentary, in one call — see the write-endpoints note above), and `POST`/`PUT`/`DELETE /landscape/assessment/{lndscpAssmtId}/callouts[/{calloutId}]`. There are **no** standalone `/dimensions`, `GET /callouts`, or commentary-only endpoints — dimensions/callouts are embedded in the details response, and commentary is saved via the overlay endpoint.
- **Auth:** every endpoint requires the `X-EGRC-UserId` header (used as `CREATED_BY`/operator identity); missing/blank → **HTTP 401**. The header name and the missing/blank guard live in one place, `util/OperatorHeader` (`NAME`, `require(username)` → `UnauthorizedException`, → 401 via `GlobalExceptionHandler`), shared by both controllers rather than each declaring its own constant/guard. Controllers read the header with `required = false` and call `OperatorHeader.require(username)`; a genuinely absent required header becomes 401 via `MissingRequestHeaderException`.
- **Responses:** all endpoints return the `ApiResponse<T>` envelope. All error→HTTP mapping is centralized in `GlobalExceptionHandler` (`@RestControllerAdvice`) — throw the domain exceptions (`BadRequestException`→400, `NotFoundException`→404, `ConflictException`→409, `UnauthorizedException`→401, `CsvValidationException`→400 w/ details) rather than building error responses in controllers/services.
- **Nulls are always serialized.** No response DTO carries `@JsonInclude(NON_NULL)` and there is no global `default-property-inclusion` — every field of every response, including the envelope's `data`/`errors`, is always present so clients see one fixed shape. Do not add `NON_NULL` to a response DTO.
- **All DB access is through Spring Data JDBC repositories** — no `JdbcTemplate`/`NamedParameterJdbcTemplate`. Values are bound as `@Query` named parameters; a variable-length `IN` list is one named collection parameter (`IN (:configIds)`). No SQL is built by string concatenation.
- **Logging:** there is no request/access filter. `ServiceLoggingAspect` adds DEBUG entry/exit + timing around all `..service..` methods and importer `processAndImport`, **summarising `MultipartFile` args (name/size only)** — never log raw file content. Controllers log each request at DEBUG with the operator id. (Tomcat access logging can be enabled via `server.tomcat.accesslog.enabled=true` if needed.)
- **Enum columns:** DB `ENUM` columns map to Java enums implementing `enums/PersistableEnum` (constant + `dbValue`, since values like `"Med Low"`/`"Poor/Fail"` aren't identifiers). Spring Data JDBC read/write is handled by the converters registered in `config/JdbcConfig`; CSV boundary DTOs stay `String` and convert via `X.fromDbValue(...)`. Response DTOs stay `String` (populated via `PersistableEnum.dbValue(...)`); the exception is `NetRiskRating`, whose API fields use `getDisplayValue()` (e.g. `"Medium-Low Risk"`).
- **JSON in columns:** `orl_lndscp_dim.RISK_AREA` is a `JSON`-typed column holding a grouped array (`[{groupName, isGroup, riskAreas:[{riskArea, riskClusters}]}]`) — read/written only through `util/RiskAreaParser` (the single source of truth: `parseStrict` for write/validation paths, `parseQuietly` for read paths, plus `lookupByRiskArea`/`riskAreaClusterMap`/`distinctRiskClusters`/`normalizeCompact`). Callout `LOCATIONS`/`BIZ_UNITS` (arrays) are stored as JSON strings. Both `RiskAreaParser` and `LandscapeAssmtCalloutService` parse via the same shared `util/StrictJsonMapper.INSTANCE` (`STRICT_DUPLICATE_DETECTION` enabled) rather than each constructing its own `ObjectMapper`. **This is deliberately a plain static instance, not a Spring `@Bean`** — registering a second `ObjectMapper` bean disables Spring Boot's autoconfigured one (the one with `JavaTimeModule` used for all HTTP request/response bodies), since that autoconfiguration is `@ConditionalOnMissingBean(ObjectMapper.class)`; a `@Bean ObjectMapper` here silently breaks `LocalDate`/`LocalDateTime` serialization on every endpoint. Parse failures are logged and degraded gracefully, not thrown, in read paths. GRC metrics are **not** stored as JSON — they are read from the per-module fact tables.
- **Lombok** is used throughout (`@Builder`, `@Getter`, `@RequiredArgsConstructor`, `@Slf4j`) — annotation processing is configured in the compiler plugin.
- **CSV download cell formatting:** every `*ConfigImportService.writeDataRows` formats null-safe cells (plain value → `""`, `LocalDateTime` → `yyyy-MM-dd HH:mm:ss` → `""`) through the shared `util/CsvFormatters.cell(...)` overloads rather than each importer declaring its own private helpers.
